# v0.2.21 release notes (2026-10-12)

All-OS release (one version bump; Windows NSIS, Linux deb + AppImage,
macOS arm64 DMG ship together). Engine pin unchanged: llama.cpp `b11407`
(sha256-verified per OS at build time; no model weights are bundled —
first-run download per ADR-008). Written by the Test and Release Engineer;
honest-wording rule applies — no aspirational claims, and the only numbers
cited are the labeled owner-local lab observations from
`docs/verification/adr-032-lightup-exactness-2026-10-12.md`, not product
performance claims.

## What is new in 0.2.21

**Cooperative batched speculative verification is now compiled into the
release build and can be activated between two peers hosting the same
pinned model profile.** This is the ADR-032 "VerifyDrafts" family: one
batched engine pass verifies a whole window of draft tokens (prefix-hash
chained, exact divergence detection with ground-truth replacement), instead
of per-token re-encoding. For a user this means:

- Two desktop installations hosting the exact same immutable profile
  (same HF repo, revision hash, file digest, quantization, runtime pin)
  can open a family session between them. Admission works like the rest of
  ModelSwarm: the coordinator presents its tracker-earned, hub-signed
  eligibility lease at session open — the same lease the existing swarm
  path already uses — and the serving peer validates it (hub signature,
  expiry, profile binding, consume right + slot, peer binding) before any
  engine work. Wrong-profile leases are refused before the engine is ever
  touched.
- **Engage gate with a never-worse guarantee:** cooperative verification
  engages only when predicted to beat the fastest eligible single host;
  otherwise it falls back to that single host automatically. A cooperative
  mode never silently ships a slowdown.
- **Honest UI:** the desktop shows one status line for the family (on:
  backend, batch window, roster size; off: the exact reason) plus a
  "test family pairing" probe button that opens one real family session
  (no prompt content) and reports the honest outcome — `opened`, or the
  exact refusal reason.

## Beta boundaries (stated plainly)

- Family verification is OPT-IN and gated: the serving side must set
  `MSP_LISTENER=1` and pin a family prompt file (`family-prompt-tokens.txt`);
  until then nothing changes and nothing is consumed.
- While a family session is active, memory use roughly doubles on the
  serving side (the llama-server sidecar plus the in-process C-API engine
  copy). Resource-governor coordination for this is queued, not shipped.
- No relay exists: peers must be directly reachable (LAN/direct). We claim
  no NAT traversal.
- The two-desktop pairing evidence and the exactness verification were run
  owner-local on a loopback machine (pinned `b11407` CPU engine,
  SmolLM2-135M Q4_K_M): committed output was token-identical to the HTTP
  ground truth in every recorded run, with verify-pass times of 12–14 ms
  per round on that machine. These are LAB numbers on one machine — not
  cross-machine, not LAN, and not a product performance claim.
- The family pairing surface is a diagnostic probe, not a chat flow;
  driving verification inside chat comes with the cooperative-plan
  Windows integration phase.

## Unchanged for everyone else

Everything shipped in 0.2.20 behaves the same: single-host chat,
msp-v1 P2P swarm serving behind the lease gate, hosting challenges,
heartbeat/lease lifecycle, the OpenAI-compatible loopback gateway, and the
tracker. Users who never opt into the family path run exactly the prior
behavior. (Internal: the release additionally fixes a latent compile
defect in the non-Windows half of the C-API adapter and adds a per-push
Linux compile gate for it — see the release handoff.)
